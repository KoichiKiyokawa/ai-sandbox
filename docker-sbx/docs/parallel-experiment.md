# 並列開発実験

## 目的と担当

ユーザーの指示に基づき、PMが3つのCodexを並列に動かします。各Codexは独立したDocker SandboxとGitブランチで作業します。共通の開始状態から変更し、PMがGitで統合します。既存のDBと未コミット変更は保持します。

| 担当 | 実装する機能 | API | 競合が予想されるファイル |
| --- | --- | --- | --- |
| 編集 | メモ本文の編集、保存、取り消し | PATCH /api/notes/{id} | api/handler.go、api/store.go、api/handler_test.go、frontend/src/App.tsx |
| 削除 | 確認後にメモを削除 | DELETE /api/notes/{id} | 同上 |
| 検索 | 本文の部分一致検索、検索解除 | GET /api/notes?q=文字列 | 同上 |

## 共通の仕様

- 編集は登録と同じ本文の入力検証を行います。作成日時は変更しません。
- 編集・削除のIDは正の整数です。不正なIDは400、存在しないIDは404、DBエラーは500とします。
- 削除成功は204です。JSON本文は返しません。
- 検索はパラメーター化したSQLで行います。%や_も通常の文字として検索します。空の検索文字列は従来の一覧です。
- 検索中の編集・削除後にも、現在の検索条件と画面の内容を一致させます。
- 新しい依存パッケージ、認証、DBスキーマ変更は不要です。
- 日本語の画面文言、読み込み中・送信中・失敗時の表示を維持します。

## PMの進め方

1. 現在のプロジェクトを一時領域のGitリポジトリに保存し、3つの担当ブランチを作ります。
2. 3つのSandboxでCodexを並列実行します。担当ごとにテスト・実装・コミットを完了させます。
3. 変更を順に統合し、Gitの競合と仕様上の衝突をPMが解消します。
4. 統合結果を元のプロジェクトへ反映します。担当の完了報告だけで完了とは判断しません。
5. Goテスト、静的解析、フロントエンドビルド、実DBでの登録・検索・編集・削除の一連の操作を検証します。
6. 実際に発生した競合と解消内容、確認結果をこの文書に追記します。

## 実行結果

3つのCodex CLIを別々のDocker Sandboxで同時実行しました。実行中の`sbx ls`で3担当がrunningであることを確認し、各担当が同じ4ファイルを変更していることも確認しました。各Sandboxには2 CPUと3 GiBを割り当てています。

| --- | --- | --- | --- | --- |

作業用Gitリポジトリは`/private/tmp/eider-parallel-20260917/`の`base`、`edit`、`delete`、`search`、`integration`です。担当別ブランチは`feature/edit`、`feature/delete`、`feature/search`、統合ブランチは`pm/integration`です。統合したソースは元のdocker-sbxにも反映しました。

## 実際に発生した競合とPMの判断

1. 削除のブランチを先にマージしました。
2. 編集のマージでは`api/handler.go`、`api/store.go`、`api/handler_test.go`、`frontend/src/App.tsx`の4ファイルで競合しました。UpdateとDeleteの両方を残し、入力検証と404処理、両担当のテスト、編集フォームと削除ボタンを共存させました。マージコミットは`2a8939e`です。
3. 検索のマージでは`api/handler_test.go`と`frontend/src/App.tsx`の2ファイルで競合しました。Listの検索引数とテストを維持し、再読み込み処理を検索条件対応版に統一しました。マージコミットは`f01a8d7`です。
4. レビュー担当が、削除版単独では再読み込み中の削除後に古いGET応答で行が復活する可能性を指摘しました。統合版では読み込み・登録・編集保存・削除中の別操作を禁止し、検索担当の要求世代番号による応答管理を採用しました。
5. 編集中の検索で入力が消えることも避けるため、編集の保存または取り消しまで別の一覧操作を禁止しました。編集・削除成功後には現在の検索条件で一覧を再取得します。

## 検証

- 各担当がHTTPテストを追加し、未実装時の失敗を確認してから実装しました。
- 各担当がmake checkと担当機能の実DB検証を実行し、成功を報告しました。
- PMが統合版でmake checkを再実行し、Goテスト、go vet、TypeScript型チェック、Vite本番ビルドに成功しました。
- PMがscripts/workflow.mjsを実行し、登録→通常検索→%・_の文字検索→編集→再検索→削除、400、404、同一本文更新、作成日時保持に成功しました。テスト作成分は削除済みです。
- 別のレビュー担当が統合版f01a8d7を確認し、重要な統合漏れやAPI不整合は見つかりませんでした。
- 比較用の接続維持スクリプトを起動し、5173・5175・5176・5177の4ポートが同時にHTTP 200を返すことを確認しました。
- ブラウザーはURLを開くところまで実施しました。ブラウザー操作ツールが接続できないため、自動フォーム操作と目視のレイアウト検証は行っていません。

## 再接続と停止

sbx v0.43.0では、最後の接続が切れると猶予時間後にVMが自動停止することをデーモンログで確認しました。ブラウザーだけを開いても接続は維持されません。4画面を継続して比較する場合は、ホストのdocker-sbx/で次を実行し、そのターミナルを残してください。

```sh
bash scripts/preview-parallel.sh
```

このスクリプトは4つのSandboxへ接続し、比較中だけ接続を維持します。グローバル設定は変更しません。Ctrl+Cで終了すると接続が閉じ、その後Sandboxは自動停止します。データは保持されます。

担当別Codexへ再接続する場合は`sbx run --name notes-edit`、`sbx run --name notes-delete`、`sbx run --name notes-search`です。各担当のDBは独立しており、統合版のDBへ検証データを移す操作はしていません。

比較を終えて停止する場合:

```sh
sbx stop notes-edit
sbx stop notes-delete
sbx stop notes-search
```

統合版は`sbx run --name notes-codex-oauth`で再接続、`sbx stop notes-codex-oauth`で停止できます。
